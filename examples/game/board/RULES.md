# 公告欄規則（Claude 與 DOT 共用）

版本 1.6 · 2026-10-25 · 對應建置文件 v0.3 的「路徑 B：存任務後領取」

這個資料夾是公告欄。每次開工都要先讀這份規則和 `PROJECT.md`。格式要照寫，辦公室畫面之後會直接讀這些檔案。

保留不變的四條原則：**派工不等於領取、停止不等於完成、不得自審、審查對準成果版本。**

---

## 1. 身分層級

| 層級 | 例子 | 說明 |
| --- | --- | --- |
| 專案 | `GAME` | 寫在 `PROJECT.md`，任務編號的前綴 |
| 主任務 | `GAME-T001` | `parent` 為 `—` 的任務，即大目標 |
| 子任務 | `GAME-T004` | `parent` 指向上一層，可以多層 |
| 主代理 | `Claude`、`DOT` | 負責任務的一方，寫在「負責主代理」欄 |
| 工作階段（worker） | `DOT-a41f9e22` | 一次實際開啟的 Claude Code 或 Codex。同一主代理可以同時有多個 |
| 執行嘗試（run） | `DOT-a41f9e22-r1` | worker 對某任務的一次嘗試。重試會另開新的 run，不覆蓋前一次 |

- 每個工作階段開工時，先在 `sessions/<session_id>.md` 登記：主代理、工具、開始時間、所在分支或 worktree，然後 commit。
- `session_id` 格式：`<主代理>-<UUID 前 8 碼>`，例如 `DOT-a41f9e22`。用 `uuidgen` 或任何 UUID 產生器，**不要用「最大編號加 1」**，兩邊同時取號會撞號。
- 子代理或分身也要登記成 worker，例如 `DOT-a41f9e22.art1`，並寫明它屬於哪個 session。
- 所有寫入都要帶 `session_id`。只寫主代理名字不算有效身分。
- 不准用別人的主代理名字或 session_id 寫入。
- 一個 session 只服務它所在 repo 的那一個專案。任務編號前綴不是本專案的，一律不能領取或寫入；批准也不能跨專案使用。

## 2. 權威分支與寫入方式

- `PROJECT.md` 寫明唯一的**權威分支**（預設 `main`）。只有已 push 到權威分支的內容才算數，其他分支上的公告欄改動一律無效。
- 每一次公告欄變更都要用一個 commit 提交：看板列＋事件＋相關的 claim 或 approval 檔，一起提交，一起成功或一起失敗。
- commit 訊息格式：`board: <type> <任務ID> by <session_id>`。
- 禁止 `git push --force`，也禁止改寫權威分支的歷史。
- **每次 pull 或 rebase 之後，不管有沒有衝突，都要重新驗證**（第 5 條的「寫入前檢查」）。rebase 沒有衝突，不代表你的改動仍然合法。
- **驗證時要看剛抓下來的遠端權威版本，不是本地 HEAD。** 本地 HEAD 可能已經包含你自己還沒 push 的 claim 或 rev，會讓你誤判。做法：`git fetch origin`，然後用 `git show origin/<權威分支>:board/BOARD.md`、`git show origin/<權威分支>:board/claims/<任務ID>` 讀取並檢查，檢查通過才把你的改動 rebase 上去並 push。

## 3. 看板與事件的分工

| 檔案 | 角色 |
| --- | --- |
| `BOARD.md` | **目前狀態的權威來源。** 誰持有、什麼狀態、哪個版本，都以權威分支上的看板為準 |
| `events.jsonl` | **稽核紀錄。** 記錄誰在什麼時候把哪些欄位從什麼改成什麼。只能追加，不能修改或刪除 |
| `claims/<任務ID>` | 領取鎖，內容見第 5 條 |
| `approvals/<批准ID>.md` | 批准紀錄，見第 8 條 |
| `handoffs/<任務ID>.md` | 交接單，只能往下追加新版本 |

如果看板和事件對不上，**不要自己用事件去修看板**。把該任務狀態改為「待核對」，追加 `inconsistency_found` 事件，交給總設計師或泓處理。

### 事件欄位（每行一個 JSON）

| 欄位 | 必填 | 說明 |
| --- | --- | --- |
| `event_id` | 是 | `<session_id>-<UTC 時間到秒>-<4 位隨機碼>`。重送同一事件時沿用原 id |
| `project` | 是 | 專案前綴 |
| `task_id` | 是 | 任務編號 |
| `type` | 是 | 見第 6 條 |
| `session_id` | 是 | 寫入者的工作階段，泓寫入時填 `泓` |
| `run_id` | 有 run 時填 | 例如 `DOT-a41f9e22-r1` |
| `claim_id` | 有持有權時填 | 見第 5 條 |
| `occurred_at` | 是 | UTC 時間 |
| `rev_before` / `rev_after` | 改看板時填 | 該列修改前後的 rev |
| `changes` | 改看板時填 | `{"欄位":["舊值","新值"]}` |
| `summary` | 是 | 使用者看得懂的工作事實，不寫內部思考、提示詞或秘密 |
| `evidence` | 有就填 | 檔案路徑、commit、成果版本 |
| `artifact_version` | 送審、審查時必填 | 例如 `v2` |
| `result` | 審查時必填 | `通過` 或 `退回` |

新版本送審或被退回後，之前的審查通過紀錄就失效。任務要完成，必須是「最新送審版本」得到審查通過。

## 4. 欄位寫入權限

| 誰 | 可以改什麼 |
| --- | --- |
| 總設計師（見 `PROJECT.md`） | 新增任務與子任務；設定負責主代理、審查者、`depends_on`；任務未被持有時重新指派；收回失聯的鎖（第 7 條） |
| 持有者（claim 屬於你的 session） | 自己持有任務的狀態：已領取 → 執行中 → 阻塞／待批准／待審查；成果版本；最後回報；釋放持有權 |
| 指定審查者 | 只限自己是審查者、且狀態為「待審查」的任務：寫入「完成」或「退回修改」，並對準送審的成果版本。退回時同時把看板的「租約到期」重設為「退回時間＋租約時間」 |
| 泓 | 全部欄位；批准；豁免子任務；裁定待核對與爭議 |
| 其他人 | 只能追加事件，例如 `handoff_requested`，不能改看板 |

- 審查者不能是該任務的持有者，也不能是做出該成果版本的 session，不得自審。
- 子任務不能擴大父任務的權限。父任務沒有被批准的對外動作，子任務也不能做。

## 5. 領取（claim）

### claim 檔內容

`claims/<任務ID>` 只有一行 JSON：

```
{"claim_id":"DOT-a41f9e22-c1","task_id":"GAME-T004","session_id":"DOT-a41f9e22","task_rev":3,"claimed_at":"2026-10-25T14:00:00Z","lease_expires":"2026-10-25T16:00:00Z"}
```

`claim_id` 用 `<session_id>-c<流水號>`，全專案唯一。

### 領取步驟

1. `git fetch origin`。
2. **領取前檢查**（讀遠端權威版本，見第 2 條），全部都要成立：
   - 負責主代理是你，你的 session 已登記；
   - 狀態為「待領取」，`claims/<任務ID>` 不存在；
   - `depends_on` 裡的每個任務都已「完成」（第 7 條）；
   - 你記下這一列目前的 `rev`。
3. 在同一個 commit 裡：新增 claim 檔；看板該列填入持有 session、claim_id、租約到期時間，狀態改「已領取」，rev+1；追加 `task_claimed` 事件。
4. push。
5. push 被拒時，先 `git fetch origin`，**從第 2 步對遠端權威版本重新檢查**，通過了才 `git rebase` 並再次 push。只要有任一項不成立（claim 檔已存在且 claim_id 不是你的、rev 變了、依賴狀態變了），就撤回你的改動並放棄這個任務。
6. push 成功後再 fetch 一次，確認 `origin/<權威分支>` 上的 claim 檔是你的 claim_id，才算領取成功。

### 寫入前檢查（每次修改自己持有的任務都要做）

fetch 之後對遠端權威版本確認：

1. `claims/<任務ID>` 仍是你的 claim_id，而且**看板上的「租約到期」**還沒過期（或目前處於租約暫停的狀態，見第 7 條）。
2. 看板該列的 rev 等於你上次寫入後的值。

如果第 1 項不符，停止寫入，追加 `holder_mismatch` 事件，等總設計師或泓處理。

如果只有 rev 不同，去讀 `events.jsonl` 裡從你上次的 rev 到目前 rev 之間的事件：

- 每一筆都是**合法的他人變更**（指定審查者的 `reviewed`，或總設計師的 `input_changed`，且都對準你這個任務），就追加 `change_acknowledged` 事件，寫明你確認了哪幾筆 event_id、接受的新 rev，然後以新 rev 為基準繼續工作。
- 只要有一筆不是上述合法變更，就停止寫入，追加 `holder_mismatch` 事件。

### 放棄領取與結案清鎖（兩件不同的事）

| | 放棄領取 | 結案清鎖 |
| --- | --- | --- |
| 什麼時候用 | 任務還沒做完，你不做了 | 任務已經結束 |
| 允許的狀態 | 已領取、執行中、阻塞、退回修改 | 完成、失敗、取消 |
| 誰可以做 | 持有者；或總設計師、泓收回鎖（第 7 條） | 持有者、總設計師或泓 |
| claim 檔 | 刪除 | 移到 `claims/_closed/<任務ID>-<claim_id>` |
| 任務狀態 | 改回「待領取」 | **維持原狀態不變**，完成仍是完成 |
| 事件 | `claim_released` | `claim_closed` |

完成、失敗、取消的任務，任何人都不能把它改回待領取。要重做就另開新任務，用 `parent` 或 `depends_on` 連回原任務。

## 6. 狀態與事件

| 狀態 | 意思 | 由誰寫入 |
| --- | --- | --- |
| 草稿 | 還缺欄位 | 總設計師 |
| 待領取 | 已指定負責主代理，等待領取 | 總設計師 |
| 已領取 | 有 claim，還沒開始 | 持有者 |
| 執行中 | 有進行中的 run | 持有者 |
| 阻塞 | 卡住，必填原因與解除條件 | 持有者 |
| 待批准 | 需要泓批准（第 8 條） | 持有者 |
| 待審查 | 已送出確切成果版本 | 持有者 |
| 退回修改 | 審查不通過，寫明要改什麼。持有者不變 | 審查者 |
| 完成 | 審查通過，指向被接受的成果版本 | 審查者 |
| 失聯 | 租約過期且沒有續約 | 任何人發現時記錄，見第 7 條 |
| 輸入已變更 | 上游成果出了新版本 | 總設計師 |
| 待核對 | 看板和事件對不上，或有爭議 | 任何人 |
| 失敗／取消 | 寫原因，保留紀錄 | 持有者、總設計師或泓 |

回合結束、工作階段關閉，或代理自稱做完，都**不等於完成**。

**退回後的流程**：退回修改 →（持有者 `change_acknowledged`，再用新的 run_id 追加 `run_started`）執行中 →（送出新版本，例如 v2）待審查。

| 時機 | 事件 type |
| --- | --- |
| 建任務、指定負責與審查者 | `task_created`、`delegated` |
| 領取、釋放、被收回 | `task_claimed`、`claim_released`、`claim_revoked` |
| 開始一次嘗試 | `run_started`（附新的 run_id） |
| 切換工作類型 | `activity_changed`（規劃／派工／執行／審核／等待） |
| 完成一個步驟，同時續約 | `progress_reported` |
| 卡住、需要批准 | `blocked`、`approval_requested` |
| 送審 | `artifact_submitted`（成果名稱、版本、位置） |
| 審查 | `reviewed`（通過或退回、檢查項目、對準的版本） |
| 確認他人的合法變更 | `change_acknowledged`（確認的 event_id、接受的新 rev） |
| 上游版本變更 | `input_changed`（總設計師寫入） |
| 結案清鎖 | `claim_closed` |
| 結束這次工作 | `turn_ended`（停在哪、下一步） |
| 批准紀錄 | `approval_recorded`（見第 8 條） |

同一任務連續退回 3 次，改為「待批准」，交給泓決定。

## 7. 租約、失聯、依賴與父任務

### 租約

- 預設租約 2 小時，可在 `PROJECT.md` 調整。每次 `progress_reported` 都同時把 claim 檔和看板上的租約到期時間延後，等於續約。
- **租約只在「已領取、執行中、阻塞、退回修改」時計時。** 待審查、待批准時暫停，因為球在審查者或泓手上；完成、失敗、取消後租約不再有意義。這些狀態下，製作者租約過期不能改成失聯，也不能被收回重派。
- **租約以看板的「租約到期」欄為準**，claim 檔裡的 `lease_expires` 只是持有者最後一次寫入時的副本。
- 退回修改時，**由審查者在退回的同一個 commit 裡**把看板的「租約到期」重設為「退回時間＋租約時間」。所以就算待審查拖得比原租約久，持有者回來時租約仍然有效，可以 `change_acknowledged` 並續約，同時更新 claim 檔的副本。
- 計時中的租約過期後，看到的人追加 `lease_expired` 事件，並把狀態改為「失聯」。持有權仍然保留，不要直接搶。
- **收回鎖**：只有總設計師或泓可以做。把 claim 檔移到 `claims/_revoked/<任務ID>-<claim_id>`，看板改回「待領取」，追加 `claim_revoked`，並在 summary 寫明原持有者已完成到哪一步、部分成果在哪裡。
- 原持有者回來時做「寫入前檢查」。如果 claim 已被收回，**不得覆蓋任何內容，也不得再做任何對外動作**（第 8 條）。把未提交的成果放到 `handoffs/<任務ID>.md` 的新版本裡，標示「失效持有者的部分成果」，交給新持有者判斷。

### 依賴

- `depends_on` 裡的任務全部「完成」之前，不得領取或開始。
- 上游任務被接受的成果版本改變時，總設計師把已開始的下游任務改為「輸入已變更」，由持有者確認是否需要重做。

### 父任務完成條件

父任務只有在以下全部成立時才能完成：

1. 所有子任務都是「完成」，或有泓的豁免紀錄（`approvals/` 裡類型為「豁免」）；
2. 沒有任何子任務處於阻塞、待批准、失聯、待核對；
3. 父任務本身送出整合成果，並由審查者審查通過。

## 8. 批准（代理不能自己產生權限）

以下事情一定要有有效批准才能做：上架或發布、付費或購買、寄信或對外發訊、刪除大量檔案、更改帳號或權限、把資料傳到新的外部服務、豁免子任務。

### 批准紀錄 `approvals/APR-<三位數>.md`

| 欄位 | 說明 |
| --- | --- |
| 批准 ID | `APR-001` |
| 類型 | 批准動作／豁免子任務 |
| 任務與成果版本 | 例如 `GAME-T005`，成果 `v2` |
| 確切動作 | 例如「以泓的開發者帳號上傳 v2 到 TapTap 測試軌」 |
| 對象與範圍 | 平台、帳號、可影響的資料 |
| 內容雜湊 | 要送出的檔案或內容的 SHA-256，沒有就寫「無」 |
| 費用上限 | 金額與幣別，或「免費」 |
| 批准者 | 一律是 `泓` |
| 記錄者 | `泓` 本人，或代記的 session_id |
| 批准來源 | 泓親自 commit：寫 commit hash；代記：寫泓原話、發話時間、在哪個工作階段說的 |
| 有效期限 | 到期後失效 |
| 狀態 | 有效／已使用／已撤銷／過期 |

### 有效條件

- **直接批准**：泓本人 commit 的批准檔。如果有啟用 commit 簽章，必須是泓的簽章。所有 session 都可以依據它執行。
- **代記批准**：泓在某個 session 裡直接對該代理說「批准」，該 session 可以代記；必須逐字引用原話和時間。代記批准**只對代記的那個 session 有效**，其他 session 不能拿來用。
- 動作、對象、版本或內容雜湊任何一項不同，批准就不適用，必須重新請求。
- 執行完畢後把狀態改成「已使用」，追加 `approval_used` 事件。
- `approval_recorded` 事件只是紀錄，不會產生權限。沒有符合上述條件的批准檔，就視為沒有批准。

### 試跑期間：對外操作一律關閉

`PROJECT.md` 的「對外操作」欄目前是「關閉」。關閉時，即使有批准，也不得執行任何第 8 條列出的動作；只能把任務停在「待批准」，等泓親自執行。

要改成「開放」之前，必須先補齊以下三件事，並通過對應測試：

1. **批准來源可驗證**：不能只看 Git 作者名稱，因為任何人都能自行填寫。改為只接受以下其中一種：泓的簽章 commit，而且遠端顯示驗證通過；或泓用自己的 GitHub 帳號在指定 issue 或 PR 留下的核准。
2. **批准一次只能被一個執行操作領用，而且只有合格者能領用**：執行前先提交 `approvals/APR-xxx.use` 鎖檔，內容為 JSON：`approval_id`、`task_id`、`session_id`、`claim_id`、`run_id`、`artifact_version`、`payload_sha256`（沒有內容就寫 `"無"`）、`used_at`。push 成功才能動手，不是做完才標記已使用。鎖檔已存在，就代表已被領用，不得再用。
   **領用資格**（`tools/verify_board.py` 會檢查）：對外操作是開放；批准檔狀態有效且沒過期；鎖檔的任務就是批准的任務；領用者是該任務目前的持有 session，claim_id 也一致；如果是代記的批准，領用者必須是代記的那個 session。批准檔的每個欄位都要填，有效期限必須是正確的 UTC 時間；領用的成果版本、任務目前的成果版本、內容雜湊都必須和批准一致。搶到 `.use` 檔但不符合資格，等於沒有領用，必須刪除並記錄 `holder_mismatch`。
3. **失去持有權的舊 worker 不能產生外部副作用**：Git 鎖不會自動停止舊程序。所以每個對外動作執行前的最後一刻，都要再 fetch 一次，對遠端權威版本確認 claim 和 `.use` 鎖都還是自己的；任一項不是，就立即停止。對外動作要選擇能事後查詢結果的方式，以便核對有沒有重複執行。
4. **最後一次檢查和實際動作之間仍有空檔**，Git 無法消除。在這段空檔裡，舊 worker 仍可能已經送出動作。開放前必須選定以下其中一種做法，寫進 `PROJECT.md`：
   - **單一執行者**：對外動作只由泓本人，或一個指定的執行程序來做；代理只負責準備內容和批准檔。這是最簡單、也最建議的做法。
   - **效果端防重**：對外服務本身支援冪等鍵或 fencing token，用批准 ID 加 claim_id 當鍵，讓重複或過期的請求在服務端被拒絕。
   沒有選定做法之前，對外操作不得開放。

## 9. 自動檢查（Git 不會替你擋自審）

**目前這套規則是「大家遵守的協作流程」，不是「程式強制的安全機制」。** 試跑已證實：跳過檢查直接把自己的任務改成審查通過，Git 仍然接受 push。要讓它變成強制，需要下面第三層。

| 層級 | 做法 | 能不能被繞過 |
| --- | --- | --- |
| 1. 代理自律 | 每次 push 前執行 `python3 tools/verify_board.py board` | 可以，代理不執行就沒用 |
| 2. 本機 hook | 把 `tools/pre-push` 複製到 `.git/hooks/pre-push` | 可以，`git push --no-verify` 就跳過 |
| 3. 遠端強制 | 權威分支設保護：禁止直接 push，只能透過 PR 合併，而且 `verify-board` 檢查必須通過 | 不能，除非有管理權限的人關掉保護 |

第 3 層需要 repo 主機支援分支保護與必要檢查，私有 repo 可能需要付費方案，請在 GitHub 設定頁確認。沒有第 3 層之前，CI 只能事後發現違規；發現時把相關任務改為「待核對」，交給泓處理。

Git 只保證提交順序，不會檢查誰有權改什麼。`tools/verify_board.py` 會讀公告欄並檢查規則，包括：審查者不是持有者也不是送審的 session、審查對準最新送審版本、claim 與看板一致、已結束任務沒有有效鎖、event_id 不重複等。

- 建議在遠端設定 CI，例如 `.github/workflows/verify-board.yml`，每次 push 到權威分支都執行一次。
- CI 失敗時，第一個看到的人把相關任務改為「待核對」，交給泓處理。違規的提交已經進了權威分支，CI 只能事後發現，不能事先阻止。要事先阻止，就得改成「只能透過 PR 合併，而且必須通過檢查」。
- 限制：session_id 是代理自己填的。要防止冒名，需要每個主代理用各自的 Git 帳號或簽章金鑰，再由腳本比對簽章者和 session 所屬的主代理。這一步還沒做。

## 10. 每次開工的固定流程

1. `git fetch origin` 並同步權威分支。讀 `RULES.md`、`PROJECT.md`、`BOARD.md`，以及 `events.jsonl` 最後 30 行。
2. 登記或更新自己的 `sessions/<session_id>.md`。
3. 處理順序：被退回給你的任務 → 你是審查者的待審查任務 → 你持有的執行中任務 → 指定給你、依賴已完成的待領取任務。
4. 一個 session 同一時間只有一件「執行中」的任務。
5. 每完成一個步驟就 `progress_reported`（同時續約），並 commit、push。
6. 做完一件回到第 1 步。沒有可做的就追加 `turn_ended`，寫明在等什麼，然後 commit、push。
